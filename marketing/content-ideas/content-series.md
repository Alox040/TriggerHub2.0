# TriggerHub Content Series

## Agent
Orchestrator and Docs Agent

## Ziel
Generate a structured build-in-public content engine for TriggerHub that supports ongoing marketing output without overstating product maturity.

## Projektanalyse
- TriggerHub has real technical proof in the trigger engine, macro engine, app facade, plugin registry foundation, tests, and Windows desktop packaging.
- Product maturity is still early: real OBS WebSocket support, Spotify OAuth, clip capture, plugin marketplace, and editor/settings/plugin UX are not complete.
- Build-in-public content should therefore emphasize implementation progress, creator workflow pain, and carefully framed alpha recruitment.

## Priorisierte Tasks
1. Create four repeatable content series anchored to the current product stage.
2. Generate 30 backlog entries with hooks, platforms, outlines, CTAs, and claim safety levels.
3. Separate immediately publishable ideas from roadmap-only and blocked claims.
4. Run QA against implementation status and update project context for future sessions.

## Zustaendige Agenten
- Orchestrator: task plan and sequencing
- Product: content strategy and 30 idea entries
- Docs: file structure, saved backlog, and content engine documentation
- QA: claim validation against the current implementation phase

## Series Overview

### 1. Dev Log
Purpose: document technical progress with honest status framing.
Primary platforms: LinkedIn, X, founder blog.
Allowed emphasis: runtime wiring, packaging, architecture, blockers, reliability work.

### 2. Automation Demo
Purpose: show how creator workflows can be translated into trigger and macro logic.
Primary platforms: short video, X clips, LinkedIn posts.
Allowed emphasis: trigger model, runtime dispatch, conceptual workflow demos.
Restriction: do not present unshipped integrations as production-ready.

### 3. Creator Problem
Purpose: articulate the pain behind TriggerHub so the audience sees the product logic before the feature list.
Primary platforms: LinkedIn, X, creator communities, blog.
Allowed emphasis: tool switching, repetitive actions, live reliability pressure, workflow visibility.

### 4. Alpha Tester Recruitment
Purpose: attract technically comfortable early adopters who can validate workflow pain and edge cases.
Primary platforms: LinkedIn, Discord, X, founder outreach.
Allowed emphasis: honest prototype stage, fast iteration, feedback loop, Windows desktop focus.

## Publishing Rules
- Publish `safe_now` ideas directly once copy is polished.
- Publish `vision_only` ideas only when clearly labeled as roadmap, direction, or concept.
- Do not publish `not_publishable` ideas externally; keep them as internal examples of claims to avoid.

## Recommended Cadence
- 1 Dev Log per week
- 1 Automation Demo per week
- 1 Creator Problem post per week
- 1 Alpha Tester Recruitment post every 1 to 2 weeks

## Workflow
1. Pick an idea from `content-backlog.md`.
2. Verify the claim safety level.
3. Adapt the entry into a channel-specific draft.
4. Run a quick QA check against `marketing/messaging/messaging-core.md` and `docs/ai-context/IMPLEMENTATION_STATUS.md`.
5. Publish or hold depending on the safety label.
